# Practising on the web — design

Status: accepted (2026-11-22); implemented by issues #68–#83.

The web app, so far a manager for the library and cards, also lets the learner
practise: the same cards, schedule and daily rules as the Android app, with progress
that meets on Convex. This supersedes "No web studying" in
[web card management](web-card-management.md).

## Decisions

| # | Topic | Decision |
| --- | --- | --- |
| 1 | Where the rules run | Study rules run as Convex functions: a **next card** query, an **answer** mutation, a foreground-time **tick** mutation and a **home summary** query. The web app stays a thin client and holds no replica of the library. |
| 2 | Fetching cards | The web fetches the next card imperatively (`convex.query`), not as a live subscription, so a phone sync landing mid-answer can't swap the card on screen. Lists and summaries stay live. |
| 3 | Per-sitting state | State that Android keeps per device and per sitting stays in the browser: cards still to recall this session (`SessionLearning`), the extra-block allowance (`PracticeBlock`) and "mute listening". It's passed to the study functions as arguments. |
| 4 | Clock | The client passes its local `day` (`YYYY-MM-DD`) and `now` (ms). Rules that depend on the local day (burials, daily counters, rollover) use them, as Android uses the device clock. |
| 5 | Read limits | Convex caps what one function may read, and the library has ~20k entries and up to ~80k cards, so no study function scans a table. See *Read-limit strategy*. |
| 6 | FSRS | A TypeScript port of java-fsrs 1.0.0 (FSRS-6), with no server-only imports so both Convex and the browser (interval previews) use it. Parity is held by fixtures generated by the real library in an Android unit test. |
| 7 | Rule parity | Kotlin `StudyRules`, `TypedAnswer`, `PracticeBlock`, `VocabularyPlacement` and `ReadingPassage` stay the reference. Each TypeScript port is held to it by shared fixtures in `content/`, run in Vitest (`convex-test` for the Convex functions) and in Android unit tests. |
| 8 | Synced settings | The fitted FSRS settings and the Gender-introduction count become synced settings, so the web schedules and limits introductions like the phone. Both are optional on push, so older APKs keep working. |
| 9 | Card IDs | The web allocates FSRS card IDs from the synced `nextCardId` setting and advances it in the same mutation. |
| 10 | Review IDs | Web answers append `reviews` rows with Android's ID format, `<key>@<review_datetime>`, and the same log JSON (including the `example` shown). |
| 11 | On-device AI | AI drafting of entries and reading passages run in the browser with WebLLM. Nothing typed leaves the browser. |
| 12 | Connection | Web practice needs a connection. There's no offline queue. |
| 13 | Out of scope | Placement on the web (beyond the optional vocabulary check), editing the daily target, backups, statistics. |

## Ubiquitous language

The terms of [noun gender](noun-gender.md) and the Android README carry over:

- **Sitting** — one run of the Study page from Start to the summary. Per-sitting state
  never leaves the browser.
- **Daily block** — today's 15 minutes. **Extra block** — +5, +10 or +15 minutes after it,
  with its own allowance of new meanings and Gender cards.
- **Wind-down** — the last two minutes of a block: nothing new is introduced.
  **Cleanup** — up to two minutes past the block for cards still to recall this sitting.
- **Started meaning** — an entry with at least one card. **Sibling skill** — a skill of a
  started meaning without a card yet.
- **Gender owner** — the one meaning of a noun whose Gender card is studied.

## Server functions

All token-gated like the rest of the web API.

- `study.next({ day, now, session, block, audio })` → the card to show (key, skill,
  entry content, shown example, FSRS card JSON or null, memory hook) or `null`.
  `session` is the per-sitting list of card keys still to recall; `block` is the extra-block
  grant and usage, or null for the daily block.
- `study.answer({ key, rating, example, day, now, session, block })` → the scheduled card,
  burials, whether a memory-hook offer is due, and the updated block usage. It reschedules
  with FSRS, writes the card's review fields, appends a review row, buries siblings, bumps
  the daily counters and leech state, and allocates a card ID for a first answer. It refuses
  an answer to a card that isn't eligible any more (deleted, suspended).
- `study.tick({ day, seconds })` → adds foreground seconds to today's total, rolling the
  daily counters over when `day` is newer.
- `study.summary({ day, now, block, audio })` → due count (display capped), seconds today
  and what's next (`session`, `extraBlock`, `moreVocabulary`, `nothingLeft`).

## Read-limit strategy

Android scans the whole library in memory. Convex functions can't, so the data gains
derived columns and indexes kept current on every write:

- **Cards** get derived scheduling columns: `due` (ms, or null for new/reset cards),
  `fsrsState`, `cardId`, `entryId` and `skill`, with indexes on `due` and on `entryId`.
  They are written by sync push, web answers, resets and a backfill migration. `sync.pull`
  strips them, so the Android wire format is unchanged.
- **Entry progress** (`progress` table): one row per started entry with the skills still
  without a card, `lexeme`, `nounKey` (bare noun + gender, for Gender owners), `rank`,
  `origin` and whether it's complete. Indexes on "started but incomplete" and on
  `nounKey`. Maintained on every card write and entry edit, backfilled by a migration.
- **Entries** get indexes on `rank` and `origin`, so new meanings are picked by walking
  ranks from the learner's starting rank instead of scanning.

A next-card query then reads: the earliest due eligible cards (a short indexed range,
skipping paused, suspended, buried and inactive ones), started-but-incomplete entries
for siblings, and a bounded walk of entries by rank for new meanings. Tests run each
function against a full seeded library and thousands of started entries.

## Sync changes

- `settings` gains `genderIntroduced` (merged like `introduced`: same day keeps the larger,
  a later day wins) and `fittedSettings` (the fit JSON or null) with its own clock
  `fittedSettingsChangedAt`; the newer change wins, and resetting to defaults is a change.
  Both are optional in `sync.push`; omitted fields keep the stored value.
- Android pushes and pulls both. Importing a fit, resetting it or restoring a backup bumps
  the clock.
- Card rows keep their wire format; the derived columns are server-only.

## Risks and trade-offs

- **Card-ID collisions.** An offline phone and the web may allocate the same card ID. IDs
  only break ties when choosing a Gender owner, so a collision can at worst pick the
  other meaning as owner; scheduling is unaffected.
- **Daily seconds undercount** when studying on two devices the same day, since the
  same-day merge keeps the larger value (unchanged from phone-to-phone sync).
- **Concurrent answers.** A web answer and a phone review of the same card merge by
  `lastReview`, as two phones do today.
- **Derived-column drift.** Every card and entry write must go through the helpers that
  maintain the derived columns and progress rows; a migration can rebuild them.
- **No offline web practice.**
